# SPEC 标识

- 编号：SPEC-001-B
- 名称：Report Lifecycle Workflow（报告生命周期管理）
- 创建日期：2026-07-13
- 状态：Completed

# 1. Background

平台已具备分析报告、报告查询和 SPEC-001-A 冻结的 Quality Scope 权限规则。质量部门需要将报告从编制、评审到正式发布的过程保留为可追溯的质量记录，而不是依赖人工口头确认或直接修改状态。

# 2. Problem Statement

当前已识别报告逻辑状态 `draft`、`reviewing`、`published`，但缺少 `reviewing → published` 的服务端审批发布闭环。由此导致：

- `reviewing` 报告不能形成正式受控报告；
- 发布责任、发布时间和状态变化原因无法统一追溯；
- 已发布报告与其形成时的质量数据关系缺少明确的快照要求。

# 3. Goals

- 建立质量部门可执行、可审计的最小报告生命周期；
- 保持已发布报告的查询规则与 SPEC-001-A 完全一致；
- 使发布后的报告及其来源数据可追溯、不可被静默覆盖；
- 不引入通用工作流引擎或复杂审批系统。

# 4. Scope

- 定义报告状态、允许的状态转换和服务端权限校验；
- 支持草稿编辑、提交评审、退回修改和发布；
- 对状态转换和发布后的关键快照写入审计记录；
- 保持报告查询的 Quality Scope 与发布状态过滤；
- 明确已发布报告的编辑与删除边界。

# 5. Out of Scope

- 通用工作流引擎、可配置审批流或多级审批；
- 自定义角色、组织级审批链和代理审批；
- 电子签名、外部签章、通知中心或邮件提醒；
- BOM、工程变更、NCR/CAPA 等未来 PLM 模块；
- 改变 SPEC-001-A 已冻结的报告读取权限矩阵。

# 6. Current Report State Analysis

当前已识别的逻辑状态为：

```text
draft
reviewing
published
```

- `draft`：可继续编制的报告；
- `reviewing`：已提交评审、尚未形成正式报告；
- `published`：正式报告，inspector 与 engineer 仅可读取此状态；
- 现有问题：缺少评审通过后的发布闭环，且发布后的数据快照与归档规则尚未形成完整规范。

实现前必须确认现有持久化状态值与上述逻辑状态的映射；不得未经迁移直接改写历史报告状态。

# 7. Proposed State Machine

```text
draft ──提交评审──> reviewing ──发布──> published
  ^                      │
  └────退回修改──────────┘
```

- `draft → reviewing`：提交评审；
- `reviewing → draft`：退回修改，必须填写原因；
- `reviewing → published`：评审通过并正式发布；
- 不允许从 `published` 直接回到 `draft` 或直接物理删除；如需修订，应创建新的草稿报告并保持旧报告历史。

第一版不实现 `archived` 状态；归档能力保留为后续规划，届时再评估状态持久化、迁移和历史读取影响。

# 8. Role Permission Matrix

下表的读取权限继承 SPEC-001-A；生命周期写权限为本 SPEC 的拟议最小规则，实施前需人工确认。

| 角色 | 查询报告 | 编辑 draft | 提交评审 | 退回修改 | 发布 |
| --- | --- | --- | --- | --- | --- |
| admin | 全部报告 | 可以 | 可以 | 可以 | 可以 |
| quality_manager | 全部质量报告 | 可以 | 可以 | 可以 | 可以（最终发布） |
| inspector | 仅 published | 不可以 | 不可以 | 不可以 | 不可以 |
| engineer | 仅 published | 不可以 | 不可以 | 不可以 | 不可以 |
| viewer | 403 | 不可以 | 不可以 | 不可以 | 不可以 |

任何状态转换都必须由服务端 Session 产生操作者身份；不得信任客户端传入的 `created_by`、`reviewed_by`、`published_by` 或角色字段。

## Decision Freeze

- 第一版状态机冻结为 `draft → reviewing → published`，以及 `reviewing → draft` 退回修改；不实现归档状态；
- `quality_manager` 拥有最终发布权限，不需要 admin 二次确认；
- inspector、engineer 和 viewer 不拥有报告生命周期写权限；
- 报告读取权限继续以 SPEC-001-A 的冻结矩阵为准。任何变更必须先更新本 SPEC 并完成 Review。

## Implementation Constraints

- 不允许通过前端按钮显示或隐藏控制状态权限；
- 所有状态转换必须在服务端校验当前状态、角色和必要所有权；
- 状态变化必须在事务边界内执行；
- 发布操作必须在同一事务内完成状态更新、发布快照生成和审计写入；
- 不允许直接修改 `published` 报告数据。

# 9. State Transition Rules

- 所有转换在服务端按“认证 → 角色/所有权 → 当前状态 → 目标状态 → 写入与审计”执行；
- 只有 `draft` 可以编辑报告业务内容；
- 提交评审前必须完成该报告既有的必填字段和来源数据校验；
- 退回修改必须记录退回原因，且只允许 `reviewing → draft`；
- 发布前必须确认报告仍处于 `reviewing`；quality_manager 可在事务边界内完成状态变化、快照和审计，无需 admin 二次确认；
- 发布不得通过前端隐藏按钮替代后端授权；
- 发布后的报告不可直接覆盖编辑、不可物理删除。

# 10. Audit Requirements

以下行为成功后必须记录审计日志：

- 创建草稿；
- 编辑草稿；
- 提交评审；
- 退回修改；
- 发布。

审计至少包含操作者、时间、报告标识、操作类型、状态前后值及必要原因摘要。不得记录密码、Token、MFA Secret、签名 URL 或敏感文件内容。

# 11. Data Snapshot Requirements

发布时必须保留可追溯快照，至少覆盖：

- 报告的标题、正文/结论、版本或生成标识；
- 发布时关联的零件版本、检测记录和分析来源标识；
- 形成报告所使用的筛选条件、时间范围或分析参数（如存在）；
- 发布人和发布时间。

已发布报告读取时应展示其发布快照或可稳定追溯到对应来源。后续检测或分析数据变化不得静默改变已发布报告的历史结论。

快照的具体数据模型、是否采用独立快照表以及历史报告回填策略，必须在实施设计阶段完成数据影响分析后确认。

# 12. Acceptance Criteria

- 未登录访问任何报告生命周期写接口返回 401；无权限角色返回 403；
- inspector 与 engineer 查询报告时仅能看到 `published` 报告；viewer 查询报告返回 403；
- 合法草稿可提交为 `reviewing`；不满足必填或来源校验时拒绝提交且不改变状态；
- 仅获准角色可以将 `reviewing` 报告发布；发布后生成审计记录和发布快照；
- 退回操作只能使 `reviewing` 回到 `draft`，且必须保存原因；
- 已发布报告不能直接编辑或物理删除；
- 已发布报告关联的零件版本、检测与分析来源保持可追溯，不因后续数据变更被静默替换；
- 所有读取与状态转换均不破坏 SPEC-001-A 的 Data Scope 和 API 权限矩阵。

# 13. Verification Plan

- 静态检查：审查所有报告写接口复用服务端 Session、既有权限能力和事务边界；
- 类型与构建：按改动范围执行 Prisma 生成、TypeScript 类型检查及必要构建；
- API 验收：以 admin、quality_manager、inspector、engineer、viewer 和未登录状态验证读取与状态转换；
- 数据验收：发布后修改关联分析或检测数据，确认已发布报告的追溯信息不被替换；
- 审计验收：逐项检查创建、提交、退回、发布都有正确的审计记录；
- 部署验收：在 Railway 环境验证迁移（如有）、状态流转、发布后查询和权限返回码。

# 14. Future Improvements

- 多级评审、会签和可配置审批人；
- 电子签名、通知与待办提醒；
- `archived` 归档状态及其历史读取规则；
- 报告模板版本与受控附件；
- 发布报告的版本比较与修订关系；
- 与 NCR/CAPA、工程变更和受控文档的关联。

# 15. Implementation Freeze

## 状态模型

第一版固定：

```text
draft → reviewing → published
```

支持：

```text
reviewing → draft
```

不实现 `archived` 状态创建。已有 `archived` 历史数据保持兼容，不进行迁移删除。

## 权限冻结

报告生命周期写权限仅限：

- admin
- quality_manager

拥有：

- 创建草稿
- 编辑草稿
- 提交评审
- 退回修改
- 发布

inspector、engineer、viewer 均不拥有报告生命周期写权限。

## 发布事务要求

`publish` 操作必须在同一个数据库事务内完成：

1. 当前状态检查；
2. 权限验证；
3. 生成发布快照；
4. 更新状态为 `published`；
5. 写入审计日志。

任何步骤失败必须整体回滚。

## 数据追溯要求

发布快照保存最小必要追溯信息：

- 报告内容摘要；
- 来源检测记录；
- 来源分析参数或结果标识；
- 零件版本；
- 发布人；
- 发布时间。

第一版不要求复制全部历史业务数据。

## Data Scope 约束

所有报告创建、提交、发布操作必须验证引用的数据属于当前用户允许的数据范围。不得通过报告绕过 SPEC-001-A Data Scope。

## 范围控制

第一版不包含：

- 通用审批引擎；
- 多级审批；
- 电子签名；
- 报告版本管理；
- 归档流程；
- 通知系统。
